# การต่อโค้ดปัจจุบันเข้ากับสถาปัตยกรรมระบบ

เอกสารนี้แยกส่วนที่ repository นี้มีอยู่แล้ว ออกจากส่วนที่ต้องสร้างเพิ่มตามแผนภาพ ข้อมูลจากระบบเดิมยังไม่มี API จึงต้องตกลงสัญญาข้อมูลกับอีกกลุ่มก่อนเชื่อมจริง

| ส่วนในแผนภาพ | ที่อยู่/สถานะใน repository | งานถัดไป |
| --- | --- | --- |
| LIFF Application | `line-liff/app/`, `components/` | หน้า UI มีอยู่ แต่คอร์ส ข้อสอบ และผลคะแนนหลายจุดยังเป็นข้อมูลตัวอย่าง |
| LINE Login | `app/liff-provider.tsx` | เริ่มต้น LIFF และอ่านโปรไฟล์ได้เมื่อกำหนด `NEXT_PUBLIC_LIFF_ID`; ต้องเพิ่มการตรวจ LINE ID token ฝั่ง server และผูกกับบัญชีระบบเดิม |
| API สำหรับ LIFF | มีเฉพาะ `app/api/omr/*` | สร้าง API ฝั่ง server สำหรับ session, สิทธิ์, คอร์ส, ข้อสอบ และค้นหา เมื่อทราบสัญญา API ระบบเดิม |
| Exam Service / ประมวลกระดาษคำตอบ | `OMRChecker/web_app/` และ `app/api/omr/*` | เชื่อมข้อสอบ/ผู้เข้าสอบจากระบบเดิม และบันทึกผลอย่างมีสิทธิ์; ปัจจุบัน OMR เป็นตัวอย่างแยกอิสระ |
| Search Service | `lib/woods.ts` มีฟังก์ชันเรียก API แต่หน้า `app/woods/page.tsx` ยังใช้ JSON | ทำ mapping ข้อมูลและตัวกรองเมื่อได้ API จริง; หน้า `/woods/id` ยังเปิดรายการตัวอย่างคงที่ |
| บัญชีผู้ใช้และคอร์สเรียน | หน้า `app/(auth)/` และ `app/course/` | แบบฟอร์มและรหัสเข้าคอร์ส/เข้าสอบยังไม่บันทึกข้อมูลหรือเช็กสิทธิ์ฝั่ง server |
| LINE Handler / Messaging API | ยังไม่มี | สร้าง webhook ที่ตรวจลายเซ็น LINE และจัดการ event/ข้อความเมื่อกำหนดพฤติกรรม Rich Menu และข้อความแจ้งเตือน |
| ระบบเดิม / Web System API / ฐานข้อมูล | อยู่นอก repository และอยู่ระหว่างพัฒนา | อีกกลุ่มเป็นเจ้าของ API; แอป LIFF ควรเรียกผ่าน API ไม่อ่านฐานข้อมูลโดยตรง |

## เส้นทางข้อมูลที่ต้องการ

1. ผู้ใช้กด Rich Menu ใน LINE OA เพื่อเปิด URL ของ LIFF บน HTTPS
2. LIFF เริ่มต้นด้วย `NEXT_PUBLIC_LIFF_ID` และเข้าสู่ระบบ LINE; browser ส่ง **LINE ID token** ให้ API ของโครงการผ่าน HTTPS
3. API ตรวจ token กับ LINE และสร้าง session ฝั่ง server แล้วเชื่อม `LINE userId` กับบัญชีของระบบเดิม ห้ามเชื่อ `userId` หรือโปรไฟล์ที่ browser ส่งมาโดยไม่ตรวจ token
4. หน้า LIFF เรียก API ของโครงการด้วย session เพื่ออ่านคอร์ส ข้อสอบ รายการไม้ และส่งคำตอบ; API ตรวจสิทธิ์ทุกครั้งก่อนเรียก Web System API
5. การตรวจภาพไปยัง OMR service; ผลตรวจต้องสัมพันธ์กับข้อสอบและผู้เข้าสอบจริงก่อนบันทึกคะแนน
6. LINE ส่ง webhook event ไปยัง LINE Handler; handler ตรวจ `x-line-signature` ก่อนประมวลผลหรือใช้ Messaging API ส่งข้อความ

การเปิด `LiffProvider` ใน layout เป็นการเริ่มต้น LINE SDK และให้สถานะกับ UI เท่านั้น **ยังไม่ใช่การป้องกัน API**. ปัจจุบันหน้าต่าง ๆ ยังคงแสดงข้อมูลตัวอย่างได้เมื่อไม่มี LIFF ID เพื่อให้พัฒนา UI ต่อได้ ห้ามใช้สถานะนี้เป็นสิทธิ์เข้าถึงข้อมูลจริง

## ข้อตกลงที่ต้องขอจากกลุ่มระบบเดิม

- Base URL สำหรับแต่ละ environment, วิธีพิสูจน์ตัวตนระหว่าง service, รูปแบบ error และ version ของ API
- Endpoint สำหรับค้นหา/ผูกบัญชีด้วย LINE user ID, รายละเอียดบัญชีและสิทธิ์ผู้เรียน
- Endpoint รายการคอร์ส ลงทะเบียนด้วยรหัส บทเรียน การอนุญาตเข้าถึง และสถานะลงทะเบียน
- Endpoint ข้อสอบ รายการคำถาม เวลาเริ่ม/หมดเวลา ส่งคำตอบ ตรวจคะแนน และบันทึกผล OMR โดยไม่ส่งเฉลยให้ผู้สอบ
- Endpoint พรรณไม้ รายละเอียด รูปภาพ pagination คำค้น และชุดตัวกรอง พร้อมตัวอย่าง response จริง
- ข้อกำหนดการเก็บภาพกระดาษคำตอบ, ระยะเวลาเก็บ, และการรับโหลดพร้อมกันอย่างน้อย 60 คนตามเป้าหมายโครงการ

เมื่อได้สัญญานี้ ให้กำหนดชนิดข้อมูลที่ `line-liff/lib/` ก่อน แล้วเปลี่ยนหน้า mock ทีละเส้นทาง เริ่มจาก login/session → คอร์ส/สิทธิ์ → ข้อสอบ/ผล → ค้นหาพรรณไม้ → LINE Handler

## ค่า environment

- `NEXT_PUBLIC_LIFF_ID`: LIFF ID จาก LINE Developers; เป็นข้อมูลสาธารณะที่ถูกฝังใน browser bundle ตอน build
- `OMR_API_URL`: URL ภายในของ OMR service สำหรับ Next.js server
- `NEXT_PUBLIC_API_BASE_URL`: URL ที่ `lib/woods.ts` ใช้อยู่ แต่หน้าไม้ยังไม่ได้เรียก; ทบทวนว่าจะย้ายมาเรียกผ่าน API server ก่อนเปิดข้อมูลจริง
- Channel secret และ credential ของ Messaging API ต้องเก็บเฉพาะฝั่ง server เมื่อเริ่มทำ LINE Handler

การทดสอบ LIFF จริงต้องมี LIFF app ใน LINE Developers, Endpoint URL ที่เข้าถึงผ่าน HTTPS และตั้งค่า `NEXT_PUBLIC_LIFF_ID` ใน `line-liff/.env.local` ก่อนเริ่ม dev/build
